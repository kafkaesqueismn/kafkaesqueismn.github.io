Turning optimisation off hid more strings than turning it on

15 Nov 2026 · 4 min read

  • malware-analysis
  • reverse-engineering
  • assembly
  • static-analyser

Running strings on a binary is usually the first step in static analysis, and my static analyser does the same thing: pull out every run of 4+ printable characters, then look for URLs, paths and registry keys. Malware authors know this, so a common trick is the stack string, where text is built in memory at run time instead of being stored in the file.

I wanted to see how much of that is the author being clever and how much is just the compiler. So I wrote one C file with five strings stored in different ways and compiled it with GCC 16 at -O0, -O2 and -Os.

The test program

static const char *literal = "http://update.example-c2.net/beacon";

char stack[32];                     /* one byte at a time */
stack[0]='c'; stack[1]='m'; stack[2]='d'; stack[3]='.';
stack[4]='e'; stack[5]='x'; stack[6]='e'; stack[7]=0;

char init[]   = "powershell -enc";  /* local array, 16 bytes */
char longer[] = "Software\\Microsoft\\Windows\\CurrentVersion\\Run";  /* 46 bytes */

unsigned char x[] = { 's'^0x41, 'e'^0x41, /* ... */ 0 };  /* "secretkey", XORed */
for (int i = 0; x[i]; i++) x[i] ^= 0x41;

All five get printed at the end, so the compiler can't throw any of them away. None of them are real indicators; they're just strings that look like the sort of thing you'd want to find.

What strings finds

String-O0-O2-Os
URL (pointer to a literal)foundfoundfound
cmd.exe (byte by byte)missingfoundfound
powershell -enc (16-byte array)missingfoundfound
...\CurrentVersion\Run (46-byte array)missingmissingfound
secretkey (XORed)missingmissingmissing

I expected the debug build to be the easy one. It's the worst of the three.

-O0: everything becomes an instruction

Without optimisation, GCC turns local arrays into instructions that write the bytes straight onto the stack. The one-byte-at-a-time version becomes one instruction per character:

movb   $0x63,-0x60(%rbp)    ; 'c'
movb   $0x6d,-0x5f(%rbp)    ; 'm'
movb   $0x64,-0x5e(%rbp)    ; 'd'
movb   $0x2e,-0x5d(%rbp)    ; '.'

Each character sits between opcode bytes, so there's never a run of 4 printable bytes. strings sees nothing.

The two arrays are built 8 bytes at a time with movabs:

movabs $0x6568737265776f70,%rax    ; "powershe" (little-endian)
movabs $0x636e652d206c6c,%rdx      ; "ll -enc\0"

The 8 characters are contiguous in the file, so strings does find something: powersheH and SoftwareH. The H on the end is 0x48, the REX prefix of the next instruction, which happens to be printable. So you get the first 8 characters of each string with junk on the end, and the rest is in separate 8-byte chunks that aren't recognisable on their own.

None of this was me trying to hide anything. I wrote normal C, and the default compiler settings did it.

-O2: back in .rodata, but in pieces

With optimisation on, GCC goes the other way. cmd.exe is 7 characters plus a null, which fits exactly in one 8-byte movabs, so the whole string ends up in a single immediate and strings finds it. The longer arrays get stored in .rodata and copied onto the stack with 16-byte SSE loads.

The 46-byte registry key needs three 16-byte copies, which is 48 bytes. Instead of handling the last 14 bytes separately, GCC does the third copy 2 bytes early so it overlaps the second. That means .rodata holds this:

Software\Microsoft\Windows\Curre
                             rentVersion\Run

which reads as:

Software\Microsoft\Windows\CurrerentVersion\Run

strings finds it, but grep CurrentVersion doesn't, because the file literally says Currerent. My static analyser still tagged it as a registry key, because its pattern matches on the Software\Microsoft\ part, but any rule looking for the exact path would miss it.

-Os: the most readable

Optimising for size, GCC skips the SSE tricks and copies from .rodata with a single rep movsb. The strings are stored whole, so everything except the XORed one shows up exactly as written.

The XOR one never shows up

The XORed secretkey is missing at every level, which is the point of doing it. GCC didn't work out the decoded value at compile time either: even at -O2 the encoded bytes are loaded with one movabs and the decode loop is still there. Something like FLOSS handles this by emulating the code and reading the decoded strings out of memory, which is a different kind of tool from strings.

What I took from this

  • Missing strings don't mean the author was hiding something. An ordinary debug build hid four out of five. Seeing powersheH in the output is a sign of stack strings, but it can just be a compiler default.
  • Exact matching on strings is fragile. The same source code gave three different results depending on one compiler flag, and one of them changed the text itself.
  • strings only finds what's stored as data. For anything built by code, you have to read the disassembly or run it.

My static analyser currently has the same blind spot as strings, since it's built the same way. Spotting runs of movb/movabs with printable immediates and putting them back together would catch the -O0 cases, and that's the next thing I want to add.
