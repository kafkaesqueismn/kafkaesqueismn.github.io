Running a privilege escalation check on my own laptop

15 Nov 2026 · 4 min read

  • linux
  • privilege-escalation
  • opsec
  • blue-team

Every privilege escalation guide for Linux starts with the same few commands. Find the SUID binaries, find files with capabilities, check what groups you're in, check sudo -l. I've run them on enough lab comps that I thought I should run them on the machine I actually use every day. Obviously.

SUID binaries

find / -xdev -perm -4000 -type f 2>/dev/null

A SUID binary runs as its owner, which is usually root, no matter who starts it. I got 23. Most are what you'd expect on any Linux install:

  • account tools: passwd, chsh, chfn, chage, gpasswd, newgrp
  • switching user: su, sudo, pkexec, ksu
  • mounting: mount, umount, fusermount3, mount.cifs
  • helpers: unix_chkpwd, ssh-keysign, dbus-daemon-launch-helper

The rest came from apps I've installed, like the Chromium sandbox helper that Electron apps ship and QEMU's network bridge helper.

None of these hand you a root shell just because they're SUID. GTFOBins lists the programs that do, and the difference is the point: a SUID find, vim or python is game over, and a SUID passwd is just how Linux works.

That doesn't make them safe, it means they're only dangerous if they have bugs. pkexec is the famous example: PwnKit (CVE-2021-4034) was a bug in it that gave root on almost every Linux distro for about 12 years. My polkit is version 128, well after the fix, but it's a good reminder that "expected" SUID binaries are exactly where people look for bugs.

Capabilities

getcap -r / 2>/dev/null

Capabilities split root's powers into pieces, so a program can get just the one it needs. The ones that matter for escalation are the ones that bypass permission checks or change your user ID.

cap_setuid on newuidmap looks scary but it's normal. It's how unprivileged users get a range of user IDs for containers, and it only lets you map the IDs listed in /etc/subuid. The same capability on python would be an instant root shell (os.setuid(0)), so it's the program that matters, not the capability alone.

dumpcap is Wireshark's capture tool. It has cap_dac_override, which means it can ignore file permissions, so in theory it could write a capture file over something it shouldn't. Two things limit this: the file is 0750 root:wireshark, so only members of the wireshark group can run it, and Wireshark's code drops everything except the capture capabilities once it starts. I'm in the wireshark group, so this one is worth checking properly.

btop is a system monitor. cap_dac_read_search lets it read any file on the system, so it can show details for processes owned by other users. Reading any file is a lot of power for a program that also reads a config file from my home folder and draws a UI.

rsh, rlogin, rcp are the old unencrypted remote shell tools from the 80s. They came in with inetutils, which I installed for something else. They're harmless here because I don't run the servers, but there's no reason to have them.

Groups

id -nG
wheel wireshark libvirt docker

This was the bad part.

  • wheel is expected. It's what lets me use sudo, which asks for my password.
  • wireshark lets me capture packets without root. Fine, but it's also what lets me run dumpcap above.
  • libvirt lets me manage VMs without root. It's close to root, because you can create a VM with the host's disk attached.
  • docker is root. Not "close to root", just root.

Docker's own documentation says the docker group "grants root-level privileges to the user". Anyone in it can start a container with the host's whole filesystem mounted:

docker run --rm -it -v /:/host alpine chroot /host sh

That's a root shell on the host, with no password and nothing in sudo's logs. Being in the docker group means sudo asking for a password is just for show, since anything running as me can skip it.

I added myself to that group so I didn't have to type sudo docker all the time, and I never thought about it again. If someone got code running as my user, through a malicious package or a browser exploit, this is the first thing they'd check.

What I'm changing

  • Leaving the docker group and using rootless Docker or Podman, which run containers without a root daemon.
  • Leaving libvirt and using sudo the few times I need to change VMs.
  • Checking btop and dumpcap properly, and removing capabilities I don't need.
  • Removing inetutils.

The SUID list turned out to be the least interesting part. The real problem was a group I added myself to because typing sudo was annoying.
